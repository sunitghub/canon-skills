# Releasing canon

For the maintainer. Consumers install from `public` (`sunitghub/canon-skills`). A plain `canon update` installs the latest verified release, and `canon update --to main` opts into the development track, so a release is what most consumers run and the point anyone can return to. This page is the one place the build and release steps are written down in order.

## Versioning

`VERSION` holds `X.Y.Z` ([SemVer](https://semver.org)): a patch for fixes, a minor for features that keep working as before, a major for a change that breaks a tool's command line or the install layout. `CHANGELOG.md` records each release in Keep a Changelog form; commits since the last release sit under `## [Unreleased]`.

A release is **not** every push. Several pushes a day share one `VERSION`, and a tag name is unique. Between releases `public` main is unreleased work that only `--to main` installs pick up; everyone else stays on the last release until the next one is published.

## The pipeline, in order

1. **Merge and push.** Merge to `main`, push `origin` (`git push origin main`), then publish to `public` (canon-skills, the install target) **only with `tkt push-main`**, never `git push public`: it pushes origin's commit and refuses one whose binaries are not released (t-b6b6). Run `scripts/install-hooks.sh` once per checkout: its pre-push hook gives a plain `git push public` the same refusal (t-4ea4); `git push --no-verify` is the deliberate override. **If the merge changed Go source** (the daemon, the Go board or the headless helper), push `origin` only, do step 2 (run `scripts/release-daemon.sh` and commit `tools/cockpit-daemon.sha256`), run `scripts/check-binaries-released.sh --download` until every line is `ok`, push `origin` again, and only then `tkt push-main`: a Go change on `public` without its released binaries leaves every install that follows `main` with nothing to fetch (t-3c9a's daemon sat on `public` unreleased for a day).
2. **If Go source changed, release the binaries first.** `scripts/release-daemon.sh` builds the cockpit daemon and the board (macOS, Linux, Windows; both from the one Go module `tools/canon-go`, t-8020) and the Windows headless helper, publishes them as GitHub releases named by each binary's source key (`tools/src-key.sh`: the git trees it is built from, so a board-only change does not re-release the daemon), and records each SHA-256 in `tools/cockpit-daemon.sha256`. Commit that manifest. Run it *before* the manifest reaches `public`: installs verify what they download against it. Release builds do not stamp `VERSION` (since t-0859): the daemon and the board read it from the install at run time, so a version bump does not change any release's bytes and needs no new binaries. (Assets published before that still carry an old stamp, which both ignore in favour of the install's `VERSION`.) A release that already exists (unchanged source) is recorded from its published asset, with a warning if today's build differs; only a manifest line that names another hash for it stops the script. A release created in the run must equal its build. `scripts/check-binaries-released.sh` is the guard to run before pushing to `public`; it is red between a Go commit and its release, by design (`--download` also re-checks every asset's hash). The binaries are built with a pinned Go (`toolchain` in `tools/canon-go/go.mod`, a `GO_TOOLCHAIN` file in the headless helper's folder), never the installed one. To pick up a Go security fix, raise the pins together (`tests/release-daemon-publish.sh` checks they agree): that changes the source folders' tree hashes, so the fix ships as new releases and older tags keep theirs. The board's **Push main to public** (`tkt push-main`) enforces this order (t-b6b6): it runs `check-binaries-released.sh --rev` on origin's commit and pushes nothing while a binary is unreleased. **When an agent runs the release** (Claude Code in auto mode), its classifier refuses `scripts/release-daemon.sh` as creating a public surface, because the script publishes GitHub releases at once. Either run it yourself (`! scripts/release-daemon.sh` in the session), or allow exactly that command once in your own, gitignored `.claude/settings.local.json`: `"permissions": {"allow": ["Bash(scripts/release-daemon.sh)"]}`. Keep the rule to that one command, never a wildcard such as `Bash(scripts/*)`, and put it in the local file, not the tracked `.claude/settings.json`, so the rule stays with you and does not reach anyone who clones canon (2026-10-28, 0.28.0).

   A fix for a bug that blocks `canon update` ships with a way out that does not need the fixed tool (a plain `git pull`), named in the CHANGELOG, because stuck installs run the old code; then look for the same class (any tracked file the app writes at run time) (`t-97b1`).

3. **To release:** first confirm `git branch --show-current` prints `main`: another session sharing the checkout can leave it on its own branch, and the bump commit then lands there (it did for 0.7.0). Bump `VERSION`, add a dated `## [X.Y.Z] - YYYY-MM-DD` section to `CHANGELOG.md` that says what matters to a user, commit, and push to both remotes. If the daemon changed since the last release, say in that section that users restart it after updating (Admin's **Restart Daemon** button): `canon update` fetches the new daemon, but a running one stays on the old version.
4. **Cut it:** `scripts/release.sh --dry-run`, read what it would do, then `scripts/release.sh`. It refuses, changing nothing, unless `VERSION` is `X.Y.Z`, the CHANGELOG has the dated section with content, `VERSION` and `CHANGELOG.md` match `HEAD`, `HEAD` is `main` and equals `public/main`, and the tag exists neither locally nor on `public`. Then it creates the annotated tag `vX.Y.Z`, pushes only that tag to `public`, and creates the GitHub release with the CHANGELOG section as its notes (`gh` must be logged in). If the GitHub step fails after the tag is pushed, it says so and prints the `gh release create` command to finish; it never deletes a pushed tag. It also builds `canon-X.Y.Z.zip` from the tag (`scripts/release-zip.sh`), attaches it to the GitHub release, and prints the manifest line for step 5; a zip that cannot be built stops everything before the push.
   **What the zip leaves out (t-3954).** `scripts/release-zip.sh` builds the end-user zip from the tag's tree minus a list it owns, `SLIM_EXCLUDE` plus the unused files of `meta/`: `tests/` (canon's own tests), `meta/` except the screenshots the board's tour shows (read from the tag's own `tools/sprint-check-app/app.html`), and the Go source in `tools/canon-go/cmd` and `internal` (`go.mod` and `go.sum` stay: `tools/cloud-env.sh` reads the pinned toolchain from `go.mod`). Everything else ships, so a NEW top-level folder is in the zip unless it is added to that list. Git installs keep everything. A tag at or before 0.20.2 was published with the whole tree: to rebuild one of those zips byte for byte (a lost asset), use the script as it was at that release (`git show c74861fd:scripts/release-zip.sh`); the current script gives the slim zip, with a different hash than that release's `releases.txt` line. `tests/release-zip-slim.sh` unpacks a built zip and fails if a file the install reads is missing, a tour image is missing or the size grows past 4.5 MB unpacked / 300 files; if a tool starts reading an excluded path, add that path to the required list in the test and take it off the exclusion list.
5. **Publish the manifest line.** Installers install a release only if `https://getcanon.dev/releases.txt` lists it (`<tag> <zip sha256> <tag commit sha>`, newest first, under the comment header). That file lives in the **canon-site** repo (its `releases.txt`, in the `site` folder there), a different write path from this repo: commit the printed line there and push it to canon-site's origin, then wait for the deploy. The highest release in this file (compared as numbers, not by file order) is what a plain `canon update` and the installers install, so publishing the line is what makes a release the default for everyone. Until it is live, `canon update --to vX.Y.Z` and the Windows installer refuse that release (they fail closed). A lost asset is rebuilt with `scripts/release-zip.sh vX.Y.Z <folder>` and uploaded with `gh release upload`; `git archive` normally gives the same bytes, but the manifest must hash the file that is uploaded, so publish the line the rebuild prints if it differs. **Then refresh the site itself** in canon-site: `npm run docs:sync` (snapshots canon-skills' `main` docs and `VERSION` into `content/upstream/`), review `git diff content/upstream`, `npm run stamp` (writes the header's version badge into `updated.js` in that repo's `site` folder), commit and push. Do it right after the tag, while `main` is the release; skipped, the badge keeps an old version (it read v0.5.0 through v0.7.0). canon-site's `t-5016` would take the badge from the manifest (`releases.txt`) instead.
5b. **Publish the integrity line (t-2af0).** `scripts/release.sh` also attaches `integrity-X.Y.Z.json` (the SHA-256 of every file in the release, built by `scripts/integrity-list.sh`) to the GitHub release and prints `<tag> <sha256 of that file>`. Add that line to **canon-site**'s `integrity.txt` (in its `site` folder, a file of its own: `releases.txt` stays three fields, because installers parse it) and push. Admin > Integrity and `sprint complete` trust the list only when its hash equals this line, so until it is live an install of that release shows "List pending" and nothing blocks. The line is not written by the release or the CI that builds the file, so a stolen release asset cannot vouch for itself.
6. **Check it:** on a machine, `canon update` (it moves to the new release), then `canon version`, then `canon update --to main` and `canon update --to latest` to go back. On Windows (a zip install) the output says `Verified vX.Y.Z`.

Nothing in the sprint close pushes a tag or refuses a push while the ticket is open: a refusal would need a Claude Code hook, and canon installs none (`t-f01d`). Close (step 9) already comes before push (step 10).

## What the verification does and does not protect

A release is installed only if the published manifest lists it. A git install (`canon update --to`) also needs the fetched tag's commit to equal the manifest's; a Windows zip install needs the downloaded zip to hash to the manifest's SHA-256, checked before anything is extracted. Anything else (manifest unreachable, no line for the tag, a malformed line, two lines that disagree, a mismatch) refuses with the reason and changes nothing. There is no override; `canon update --to main` is the way out.

It does **not** verify `main`, which moves with every change, and it cannot protect against someone who controls `install.sh`/`install.ps1` themselves: `getcanon.dev/install.*` rewrites to the same GitHub repo as the zip, so such a person could remove the check. What it adds is a second write path (the canon-site repo) that must agree with the zip, and protection against a corrupt, truncated or changed download. The manifest fetch is a plain GET of a static file; it carries no identifier. `CANON_MANIFEST_URL` only moves where the manifest is read (tests use `file://`) and is not a skip, but whoever controls the installer's environment can point it at a manifest they wrote: the same trust boundary as the installer script itself.

## Rolling back (what a consumer does)

```bash
canon update --to v0.3.0     # install that release now; the daemon and projects are refreshed as in a normal update
canon update                 # the next plain update goes to the latest release again
canon update --to main       # the development track (not verified); a plain update keeps following main
canon update --to latest     # back to the verified releases
```

A plain `canon update` follows the latest verified release (from v0.4.0 on: v0.3.0 has the older updater, where a plain update refuses as "pinned" and `--to latest` is unknown, so a v0.3.0 install runs `canon update --to main` or `--to vX.Y.Z` once); `--to vX.Y.Z` is not sticky (like most software, nothing remembers an older pin, so a rollback lasts until the next update). `--to main` is remembered in an untracked `.canon-track` file (`main`); `--to latest` or a release clears it. An install made before releases were the default (on `main`, no marker) moves to the latest release on its next plain update with a one-time message; one with local commits, uncommitted changes or another branch refuses and says so (`canon update --to main` keeps it on main). On a git install the tag is fetched into the shallow clone; on a Windows install made by the one-line installer (a zip, no git) the installer is re-run with `CANON_REF` (`latest`, `main` or `vX.Y.Z`) and copies that release's verified zip over the install (files only the newer tree had are left behind, as in any Windows update). `--to` accepts `latest`, `main` or `vN.N.N`. Binaries need nothing extra: an older tree names its own release assets, which are never overwritten.

`v0.3.0` is the first tag and already contains `--to`. An install made before `--to` existed cannot use it until it has updated once: run a plain `canon update` first (it takes main), then `canon update --to vX.Y.Z`.
