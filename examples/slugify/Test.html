Why every skill needs an evals folder

A real walkthrough with a tiny skill, slugify — two separate lessons, each with its own real catch: having evals at all, and having a human check what the evals claim is correct.

0. The premise, pressure-tested

Fair pushback: "couldn't you just keep tweaking the skill until it works?" Yes — once, in one session, by the person who happens to be paying close attention. What tweaking-by-feel doesn't give you:

Regression protection isn't free without a fixed test set. You only re-check what you remember to re-check. Six months from now, someone edits this skill for an unrelated reason and has no way to know the café case or the apostrophe case ever existed — unless something wrote them down.

The evals folder isn't what gets the skill right the first time. It's what tells the next person — or the next edit — whether it's still right.

1. The skill, with two independent bugs

examples/slugify/no-evals/SKILL.md: seven steps, lowercase → hyphenate whitespace → strip characters → collapse → trim. Two things are wrong with it, neither obvious from reading it once:

  • Step 3 accidentally keeps apostrophes in the character allowlist.
  • Nothing transliterates accented characters — they're just dropped.

The "é" is silently dropped, not transliterated — "Café" becomes "caf," not "cafe." Nobody tests an accented character when the happy path already worked.

Nudged for one more case — and the twist

A follow-up asked the same agent for "a title with a non-English or accented character." It wrote this:

{
  "prompt": "Slugify this title: \"Café Rules — 2024\"",
  "expected_output": "caf-rules-2024",
  "expectations": [
    "The accented character (é) is dropped rather than transliterated to 'e' or
     kept as-is, per the rule that only lowercase letters, digits, and hyphens survive"
  ]
}
The agent's own reasoning called this "the case most people miss... a real product/customer-title footgun" — and then wrote the bug into the eval as correct anyway. It re-derived "expected" from the skill's own underspecified rule instead of judging what should actually happen. An eval like that doesn't catch the bug — it certifies it.

Closing the loop — with-evals-fixed/

Both bugs traced to specific, narrow instructions. Two small edits, nothing else touched:

3. Remove any character that isn't a lowercase letter, digit, or hyphen.
   (dropped the "or apostrophe" carve-out)

1. Transliterate accented or diacritic characters to their closest plain-ASCII
   equivalent (é → e, ñ → n, ü → u, ç → c, etc.).
   (added as a new first step)

Two different lessons, deliberately kept separate: having an evals folder turns "seems fine" into a real, reproducible signal on the very first run — the apostrophe bug needed no human correction at all, just one prompt to an agent. Having a human in the loop is what catches the case where the eval itself is wrong — an agent that mechanically re-derives "expected" from the skill's own flawed instructions will certify the bug instead of catching it. Neither replaces the other. And neither one is really about getting the skill right today — it's about whether anyone can tell, six months and one more edit from now, that it's still right.
