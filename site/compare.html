In practice

Where each one wins.

Canon doesn't replace a runtime or a terminal. It answers a different question: is the work done?

vs Herdr

Herdr keeps the herd alive. Canon decides what counts as done.

Herdr is a runtime: a server owns the terminals, agents keep working while you are away, and it tracks whether each one is blocked. Canon's Cockpit does a lighter version of that for one machine. What Herdr does not document is a plan, acceptance criteria or a review gate.

Herdr wins on multiple machines, SSH and the number of agent CLIs it detects. Use both: canon's CLI and skills run inside any terminal, including a Herdr pane.

vs tmux

tmux sees panes. Canon sees tickets.

tmux lets programs keep running after you detach, and it has no idea an agent is in one. Canon treats each piece of work as a ticket with a plan, a checklist and a verdict, and shows its state on a board.

tmux wins on being everywhere, dependency-free and scriptable. Use both: run the agent that runs sprint start in a tmux pane.

vs Warp

Warp moves the work into its window. Canon keeps it in your repo.

Warp pairs a terminal with agents, planning and code review, and Factories adds team orchestration, approval gates and run scoring across Slack, Linear, Jira and GitHub. Canon stays local: plans and verdicts are markdown files in your repo, graded by a second agent, enforced by the CLI.

Warp wins on team workflows, integrations and cloud agents. Use both: canon's sprint runs under Claude Code, which Warp can also run.
